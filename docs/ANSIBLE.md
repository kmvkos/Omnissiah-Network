# Развёртывание с АРМ через Ansible

Первая очередь: установка Omnissiah и Magos, регистрация узлов в БД,
сертификаты, HTTPS/mTLS, запуск через systemd и проверка heartbeat.
Playbook не создаёт туннели и не меняет маршруты, NAT, sysctl или правила firewall.
Адреса VPN в inventory резервируют записи для дальнейшей настройки в Omnissiah.
Управляющий обмен при установке идёт через локальную сеть, независимо от VPN.

Для отдельной ВМ control и запуска из скачанного ZIP используйте
[CONTROL.md](CONTROL.md). Он поддерживает SSH/sudo-пароли через Vault и вход
по SSH-ключу. Команды ниже описывают также путь из Git-клона с SSH-ключом.

## 1. Подготовить ВМ

- Одна ВМ Omnissiah и минимум одна Magos; 3, 5, 10 и больше задаются группой `magos`.
- Debian 13 amd64 без рабочего стола, SSH server.
- Уникальные стабильные IPv4-адреса, доступные с АРМ.
- Учётная запись для SSH с правами sudo либо первоначальный SSH-доступ root.
- Доступ к Debian-репозиториям и PyPI для установки пакетов.
- Снимки чистых ВМ перед первым запуском.

Python на ВМ можно не устанавливать вручную: playbook сначала использует `raw`
по SSH для его установки, затем ставит системные пакеты и venv с зависимостями.
SSH и возможность получить права root должны существовать до этого шага.

## 2. Подготовить АРМ

На Linux или в WSL нужен Python 3.12+ и git. Например, на Debian 13:

```bash
sudo apt-get update
sudo apt-get install git python3 python3-venv openssh-client
git clone --branch feat/ansible-bootstrap https://github.com/kmvkos/Omnissiah-Network.git
cd Omnissiah-Network
python3 -m venv .ansible-venv
source .ansible-venv/bin/activate
python -m pip install -r ansible/requirements-control.txt
cp ansible/inventory.example.yml ansible/inventory.yml
```

Репозиторий приватный: используйте свой обычный GitHub SSH- или HTTPS-доступ.
Для Git-клона изменения проекта должны быть закоммичены. Из распакованной
папки playbook собирает пакет без Git. Локальные inventory, секреты и artifacts
исключаются из пакета узлов и из Git.

## 3. Заполнить inventory

В `ansible/inventory.yml` поменяйте `ansible_user` и `ansible_host` на свои значения.
Роль задаётся группой `omnissiah` или `magos`, имя узла — именем хоста inventory.
Допускаются латинские буквы, цифры, `_` и `-`; первая буква латинская,
длина имени — до 15 символов. Имена и адреса должны быть уникальными.

`ansible_host` — реальный адрес SSH/HTTPS в локальной сети.
`omnissiah_vpn_address` — отдельный будущий адрес внутри VPN.
Начальная сеть Omnissiah имеет префикс /16…/29; адреса Magos должны попадать в неё.
Изменения VPN-адресов после первого развёртывания делаются в приложении:
повторный playbook их не перезаписывает.

Для первого стенда оставьте `10.77.0.1/24`, `.2/32`, `.3/32`, если эта сеть
не пересекается с используемыми сетями. До этапа настройки VPN эти адреса
не назначаются интерфейсам.

HTTPS по умолчанию слушает TCP 8443 на `ansible_host`.
Внешние firewall должны разрешать SSH с АРМ и HTTPS между узлами и с АРМ.
Сам playbook firewall не изменяет.

## 4. Проверить SSH

Для автоматической проверки из корня проекта:

```bash
bash control-install.sh --ssh-only
bash control-install.sh --access-only
```

Первый режим проверяет SSH, второй — sudo/root на каждом узле без установки
компонентов и без требования Python на ВМ. Подробности ошибок sudo —
в [CONTROL.md](CONTROL.md#отдельно-проверить-sudo).

Установите SSH-ключ своего АРМ для выбранного пользователя на каждой ВМ,
например через `ssh-copy-id`. При первом входе проверьте и подтвердите
отпечатки SSH-ключей ВМ. Проверка host key в Ansible включена.

Из каталога `ansible/`:

```bash
ansible-inventory -i inventory.yml --graph
ansible-playbook -i inventory.yml site.yml --syntax-check
ansible-playbook -i inventory.yml site.yml --tags prepare
```

`--tags prepare` проверяет inventory и готовит архив только на АРМ, без доступа
к ВМ. Полный запуск выполняйте без фильтра тегов.

Проверку `ansible -m ping` используйте после установки Python: этот модуль
требует Python, в отличие от начального шага `raw`.

## 5. Развернуть

Из корня проекта с активированным окружением АРМ:

```bash
bash ansible/deploy.sh --ask-become-pass
```

При уже настроенном sudo без пароля или SSH от root параметр
`--ask-become-pass` можно убрать. Первую установку запускайте для всего inventory:
выдача сертификатов и регистрация зависят от всех перечисленных узлов.
`--check` не поддерживает полный bootstrap; для предварительной проверки
используйте `--syntax-check`. Не отключайте проверку host key и TLS.

Playbook проверяет inventory и sudo/root на всех узлах до установки,
останавливает весь запуск при ошибке любого узла, переносит runtime-исходники
с control, устанавливает Python и пакеты, создаёт отдельный системный аккаунт,
готовит сертификаты, регистрирует узлы, запускает службы и выполняет
heartbeat через mTLS, а также HTTPS-запрос Omnissiah → Magos.

## 6. Открыть интерфейс

Откройте `https://<IP-Omnissiah>:8443/login`. Браузер сначала не доверяет
созданной CA: публичный сертификат сохранён на АРМ в `ansible/artifacts/ca.crt`.
Для постоянного доступа импортируйте его в хранилище доверенных CA браузера/ОС.
Адрес в URL должен совпадать с IP из inventory, который включён в SAN сертификата.

Логин по умолчанию: `admin`. Случайный пароль создаётся один раз на Omnissiah:

```bash
sudo cat /var/lib/omnissiah-network/admin-password
```

Пароль не возвращается в выводе Ansible и не попадает в Git.
Для своего первоначального пароля можно использовать `omnissiah_initial_admin_password`
в отдельном зашифрованном Ansible Vault-файле и передать его через
`-e @ansible/vars.secret.yml --ask-vault-pass`; длина — минимум 12 символов.
При повторной установке пароль существующего пользователя не меняется.

В интерфейсе будут видны Omnissiah и Magos. Heartbeat показывает работу агентов;
VPN-статус пока неактивен, потому что туннели ещё не настроены.
Начальные учётные данные старого `init_db()` этим способом не создаются.

## Что установлено

| Элемент | Путь / поведение |
| --- | --- |
| Исходники и venv | `/opt/omnissiah-network/` |
| БД, состояние, bootstrap | `/var/lib/omnissiah-network/` |
| Служба приложения | `omnissiah-network.service` на каждой ВМ |
| Backend Omnissiah | `127.0.0.1:33787`, один Gunicorn worker |
| Backend Magos | `127.0.0.1:5001`, один Gunicorn worker |
| Доступ к сети управления | nginx HTTPS на `<ansible_host>:8443` |
| Приватный ключ CA | Только на Omnissiah, `pki/ca/ca.key`, root/0600 |
| Приватный ключ узла | Создаётся на этом узле; передаётся только публичный CSR |

Magos требует сертификат клиента для HTTPS. На Omnissiah вход через браузер
доступен без клиентского сертификата; маршруты агента требуют mTLS и проверяют
соответствие CN сертификата имени узла. nginx перезаписывает служебные заголовки,
а backend доступен только через loopback. Другие API требуют веб-аутентификации.

## Повторный запуск и диагностика

Повторите ту же команду. CA, приватные ключи, пароль администратора, мастер-ключ,
БД и настройки VPN сохраняются. Сертификат перевыпускается при изменении SAN
либо приближении срока истечения, с сохранением ключа узла.
Изменение IP в inventory обновляет сертификаты и управляющие адреса;
смена имени или роли существующего узла требует отдельной миграции.
Удаление хоста из inventory автоматически не удаляет его из БД и не отзывает сертификат.

На любой ВМ:

```bash
sudo systemctl status omnissiah-network nginx
sudo journalctl -u omnissiah-network -n 100 --no-pager
sudo nginx -t
```

Установщики `install.sh`, `start.sh` и `agents/run.py` этим playbook не запускаются.
Агенты начинают в режиме `manage_wireguard: false`: без регистрации WG-ключей,
поднятия интерфейсов и сбора VPN-логов. Запуск без root-привилегий намеренный;
сетевые команды существующего приложения требуют последующей проработки прав.
Это установка управляющих компонентов, а не подтверждение работоспособности туннелей.

## Проверка разработки

```bash
python -m pip install -r requirements.txt pytest PyYAML jinja2
python -m pytest tests -q
```

Тесты проверяют повторную выдачу сертификатов, сохранение ключей и состояния,
вход в интерфейс, heartbeat с привязкой к сертификату и реальное TLS-соединение
с отклонением неправильного имени сервера, недоверенной CA и отсутствующего
клиентского сертификата. Полный playbook с apt/systemd ещё нужно выполнить
на подготовленных Debian-ВМ.
