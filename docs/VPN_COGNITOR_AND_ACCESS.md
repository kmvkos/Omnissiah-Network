# Cognitor, защищаемые объекты и политики — актуальная концепция VPN v2

## Компоненты

- **Omnissiah** — управляющий сервер: Web UI, БД желаемого состояния,
  аутентификация, план изменений, mTLS-команды Magos. Он **не**
  является WireGuard peer и не передаёт VPN-трафик.
- **Magos** — WireGuard VPN-шлюз, агент, точка применения маршрутов,
  политик и сетевых ограничений.
- **Cognitor** — индивидуальный WireGuard-клиент (ноутбук, телефон,
  сервер), прикреплённый к одному родительскому Magos.
- **LAN-узел** — хост/подсеть за Magos; устанавливать WG на каждый такой
  хост **не требуется**. Нужны маршрутизация, обратный путь и политики.

Текущий Full Mesh связывает Magos01–03 прямыми туннелями. Управление
Omnissiah работает отдельно от туннелей по аутентифицированному mTLS.

## Что такое защищаемый объект

Защищаемый объект — ресурс, к которому система **контролирует доступ**:
- индивидуальный IPv4-адрес /32 (сервер, IPMI, БД);
- явно заданная сеть CIDR за конкретным Magos (например 172.16.40.0/24);
- в перспективе — группа однотипных ресурсов или сервис на конкретном порту.

В старом проекте есть таблица `ProtectedObject` с CIDR `network`,
привязкой к `General.node_id`, интерфейсом и описанием. Это
**инвентаризация/намерение**, не доказательство применённого firewall.

## Что такое политика доступа

Правило связывает **источник → назначение → протокол/порт → решение**.
Например: `cognitor-admin → 172.16.40.10/32 → TCP/22 → разрешить`.
Сохранять объекты и правила в БД недостаточно: Magos должен получать
верифицируемую конкретную конфигурацию, применять её идемпотентно,
проверять счётчики/трафик и отчитываться об ошибке/откате.

В старой БД есть `AccessPolicyRule`, `PolicyGroup`, `FirewallRule`.
Это legacy-модель и **не** готовый доказанный enforcement-путь VPN v2.

### Три отдельных механизма

1. **WireGuard AllowedIPs** — соответствие публичного ключа IP-адресам
   и криптографическая маршрутизация; это не замена межсетевому экрану.
2. **Linux routing** — доставка пакета до ресурса и наличие обратного
   маршрута. Не назначать 0.0.0.0/0 без отдельного согласования.
3. **Фильтрация на Magos** — независимая политика по исходному клиенту,
   назначению, протоколу и порту; по умолчанию запрет клиентского
   доступа к защищаемым объектам без правила.

Потоки могут обходить Magos: такой трафик его локальные правила не
контролируют. Защиту нельзя обещать без проверки реального data path.
Механизмы mTLS, SSH и управления нельзя случайно блокировать
пользовательскими правилами.

## Cognitor: этап 1 — только черновик

Новый маршрут `/vpn/cognitors` требует аутентифицированного администратора
и CSRF для POST. При создании:
- выбирается существующий Magos;
- проверяются уникальное имя, клиентский public key WireGuard в Base64,
  один свободный IPv4 /32 внутри пула Omnissiah, коллизии с Magos,
  Omnissiah, старым `General` и новым реестром;
- сохраняется строка `vpn_cognitor_drafts` со статусом `draft`;
- **не** генерируется приватный ключ на сервере: клиент создаёт его
  самостоятельно и передаёт в вебку только публичный;
- нет вызовов `wg`, `ip route`, shell, старого `/add_peer`,
  HTTP-команды, фонового применения или скачивания конфигурации.

Новая таблица не связана с legacy `General(role='Cognitor')`, потому
что прежние обработчики могут отправлять пиры напрямую и обойти mTLS/root
RPC. Таблица регистрируется при импорте Blueprint; существующая
`deploy/bootstrap.py` вызывает `db.create_all()` во время
стандартного полного Ansible-обновления. Резервная копия БД обязательна.

### Предстоящие этапы

1. **Предпросмотр применения Cognitor**: отдельно проверять фактические
   peer/route и точку владения Magos; запрет конфликтов; UUID операций.
2. **Безопасный root RPC**: отдельная контролируемая
   операция add-only client peer с rollback и persist config на Magos;
   нельзя использовать legacy /add_peer и прямой sudo из Flask.
3. **Выдача конфигурации клиента**: приватный ключ остаётся на клиенте,
   сервер выдаёт только необходимые параметры подключения. Публичный
   доступ/endpoint Magos, AllowedIPs и обратные маршруты задаются явно.
4. **Статусы и отзыв доступа**: после mTLS-ACK и WireGuard handshake
   различать `подготовлен`, `применён`, `активен`, `отозван`.
   Применение удаления и очистка маршрутов требуют отдельной безопасной
   транзакции.
5. **Политики**: группы клиентов, защищаемые IP/CIDR, TCP/UDP/ICMP,
   порты, default deny, журналируемый dry-run/apply/rollback. Поддержка
   LAN за Magos только после тестирования маршрута туда и обратно.

**На текущем этапе регистрация Cognitor не создаёт работающего VPN-клиента
и не предоставляет доступ к ресурсам.** Черновой PR не разворачивает
изменения автоматически; live Full Mesh остаётся нетронутым.


## Cognitor: этап 2 — безопасный предпросмотр через Magos

Для каждого черновика появилась ссылка «Проверить подключение».
Omnissiah вызывает `cognitor-preview` по mTLS, агент Magos отправляет
действие через Unix RPC в локальный root-helper. Привилегированный процесс
наблюдает `wg0`, публичные peer AllowedIPs и маршруты `main`, проверяет
root-owned `/etc/wireguard/wg0.conf`. Сверка конфигурации на диске с
ядром — обязательная: добавление клиента после изменения только памяти
или только файла небезопасно.

Принимаются только IPv4 /32, уникальная пара public key/IP, отсутствие
конфликтующего host route /32, отсутствие пересечения с IP управления.
Ответ сообщает, что конфигурация может быть добавлена, сколько пиров
подключено и SHA-256 отпечаток прочитанного состояния. **Приватные
ключи, конфиг WireGuard и состояние других клиентов не раскрываются.**
Результат read-only `writes_performed: false`.

**Особенно важно:** это НЕ выдача разрешения на последующий Apply.
Перед отдельной будущей операцией записи root-helper будет обязан
повторить весь preflight под одним lock и связать результат с UUID
транзакции. Нельзя применять устаревший preview.

### Минимальная лабораторная проверка перед применением

1. Сначала проверьте, что Magos03↔Magos01 и Magos03↔Magos02 работают.
2. Откройте Cognitor → «Проверить подключение». Ожидается
   «Предварительная проверка пройдена», два уже подключённых пира и
   «Изменений выполнено: 0».
3. Если проверка не проходит, **не исправляйте через ручной wg set**.
   Сверьте `wg show wg0`, `ip -4 route show dev wg0`, права на
   `/etc/wireguard/wg0.conf`, штатные логи агентского сервиса.
4. Запись client peer пока намеренно не реализована. Не путайте успех
   preflight с готовым клиентским WireGuard-туннелем.


## Cognitor: этап 3 — экспериментальный Add-only Apply и Debian client

Реализованы отдельное действие `cognitor-add` и CSRF-подтверждение через
веб-интерфейс Omnissiah. Это **не** общий Mesh Apply. Команда выполняется
только через mTLS → агент Magos → Unix socket → root-helper после проверки
UUIDv4, ревизии read-only preview, списка доверенных IP управления и
трёх явно включённых параметров маршрутизации.

При применении под общим `mesh-transaction.lock` заново проверяются
пиры, маршруты и файл на диске. Затем создаётся root-only архив исходного
`wg0.conf` и состояния WireGuard, durable UUID ledger и журнал.
Изменения ограничены добавлением *одного* нового public key с
`AllowedIPs=<IP Cognitor>/32`, *одного* маршрута
`ip route add <IP>/32 dev wg0 table main` и атомарным сохранением
отдельной секции Cognitor в управляемом `wg0.conf`.
Только после проверки live-пиров, маршрута и сохранённого файла Magos
сообщает `committed`, а Omnissiah ставит `applied`.

Существующие пиры не синхронизируются заново при успехе. При обычной
ошибке пытаемся убрать только нового пира и принадлежащий ему маршрут;
если произошла ошибка отката или аварийный SIGKILL, журнал требует
**ручной сверки** и запрещает новые изменения до разрешения ситуации.
Автоматическая загрузочная recovery для Cognitor не реализована.

**Важно:** `applied` означает, что клиент настроен на Magos. Факт
подключения смотрим отдельно по read-only странице «Проверить
соединение», получающей `wg show` через mTLS: пир обнаружен, свежесть
handshake, rx/tx.

### Клиент Debian без агента и без Ansible

Создание и импорт клиентской конфигурации делается *только* на Debian
Cognitor. Приватный ключ, созданный локально с `umask 077`, должен
остаться на клиенте. Скрипт `scripts/cognitor_debian_setup.py`
запускается локально с `sudo`, валидирует параметры WireGuard и
создаёт новый `/etc/wireguard/wg0.conf` (root-only mode 0600) **без
перезаписи существующего файла**. Не активирует интерфейс.

Пример **для клиента, прикреплённого к Magos03** (реальный родитель,
IP и endpoint следует сверить с записью в Omnissiah):

```bash
sudo apt install wireguard-tools
sudo python3 cognitor_debian_setup.py \
  --private-key /home/<CLIENT_USER>/wireguard-client/cognitor.key \
  --address 10.77.0.5/32 \
  --parent-ip 10.77.0.4/32 \
  --parent-public-key <PUBLIC_KEY_MAGOS03> \
  --endpoint 192.168.32.172:51820
sudo wg-quick up wg0
sudo wg show wg0
ping -c 3 10.77.0.4
```

Только после успешного рукопожатия разрешайте запуск при загрузке
(`sudo systemctl enable wg-quick@wg0.service`). Если проверка не
прошла, проверьте UDP endpoint, маршруты, публичные ключи и журнал
транзакции Magos. Не пересоздавайте клиентские ключи без необходимости.

### Ограничения и меры безопасности

- Это **лабораторный этап**. Политики доступа к защищаемым объектам в VPN
  v2 ещё не применяются, поэтому нельзя считать клиентские ресурсы
  изолированными до проверки правил на Magos. Не используйте эту версию
  для промышленного доступа к критичным LAN.
- Конфигурация клиента по умолчанию маршрутизирует **только** VPN IP
  родительского Magos, не `0.0.0.0/0`. Для доступа через другие Magos
  потребуется отдельная согласованная политика, forwarding и симметричная
  маршрутизация обратного трафика.
- Текущая сверка Mesh Desired/Actual учитывает только Mesh-пиров Magos;
  после добавления Cognitor на выбранном Magos она может показать
  ожидаемое расхождение. Пока root-helper блокирует старый mesh-only
  Apply, если у Magos есть подключённые управляемые Cognitor.
- После потери ответа на Apply запрещено повторять кнопку: root мог
  выполнить операцию. Проверьте root-журнал и UUID, затем согласуйте
  БД Omnissiah с фактическим состоянием Magos.
- Снапшот ВМ, доступ к консоли гипервизора и рабочий канал mTLS обязательны
  перед первым live Apply.
