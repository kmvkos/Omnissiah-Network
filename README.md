# Omnissiah Network

Система централизованного управления распределённой VPN-сетью на базе WireGuard.
Сервер Omnissiah управляет узлами, соединениями и политиками доступа через
веб-интерфейс; агенты Magos применяют настройки на Linux-узлах и передают состояние.

Это личный проект для собственной инфраструктуры и сетевого стенда.
**Текущий этап — прототип, подготовленный к восстановлению и стабилизации.**
Наличие функций в исходниках ещё не подтверждает их сквозную работоспособность.

## Компоненты

| Компонент | Назначение | Реализация в этом репозитории |
| --- | --- | --- |
| **Omnissiah** | Сервер управления, веб-интерфейс, хранение конфигурации и состояния | `src/`, `templates/`, Flask + SQLAlchemy + SQLite |
| **Magos** | Управляемый VPN-узел: WireGuard, применение конфигураций, heartbeat и статистика | `agents/`, Python + Flask |
| **Cognitor** | Конечный клиент VPN-сети | Роль узла и генерация клиентской конфигурации; отдельного каталога приложения Cognitor нет |

В текущем коде Omnissiah также может быть узлом WireGuard. Разделение сервера
управления и пути пользовательского трафика — вопрос дальнейшей стабилизации,
а не уже гарантированное свойство системы.

## Что реализовано в коде

- Создание и управление узлами Omnissiah, Magos и Cognitor.
- Генерация конфигураций WireGuard, ключей и связей между узлами.
- Развёртывание и обновление агентов через SSH.
- Защищаемые сети, группы и правила политики доступа, генерация правил iptables.
- Heartbeat, сведения о состоянии узлов, счётчики и журнал трафика.
- Генерация сертификатов, поддержка mTLS и шифрования конфигураций.

Эти возможности требуют проверки на Linux-стенде. Поддержка mTLS в коде
не означает, что все маршруты API уже требуют аутентификации.

## Структура

```text
src/                  сервер, модели, API и сетевые утилиты
agents/               исходники агента Magos
templates/            шаблоны веб-интерфейса
tests/                существующие тесты из исходного проекта
scripts/              анализ исходников и диагностика WireGuard
systemd/              существующий вспомогательный unit wg-auth.service
docs/                 состояние проекта, подготовка стенда и справочные материалы
migrate_*.py          существующие миграции базы данных
mtls_utils.py         создание сертификатов
requirements.txt      зависимости сервера из исходного проекта
.env.example          шаблон локальных переменных без секретов
build.sh              сборка архива из закоммиченных файлов
```

Пути и имена модулей сохранены, чтобы начать исправления с исходной версии.
Обозначения `NMC WG`, `nmc_*` и `omnissiah-nmc` пока встречаются в коде и скриптах.

## Подготовка к запуску

Первое развёртывание выполняйте на отдельных Linux-ВМ: приложение изменяет
WireGuard, маршруты, firewall, nginx и настройки sudo. Целевой первый стенд:
одна ВМ Omnissiah и две ВМ Magos.

Подробные команды и ограничения: [подготовка стенда](docs/SETUP.md).
Перед запуском понадобятся системные утилиты WireGuard, Python-окружение,
локальный `.env` с новыми секретами и проверенные права на сетевые операции.

В текущем коде веб-приложение слушает TCP **33787**, API агента — TCP **5001**
(в `agents/run.py` предусмотрен переход на 5002, если порт занят).
Порты WireGuard задаются конфигурацией узлов.
При создании пустой БД `init_db()` создаёт пользователя **Adeptus**
с паролем **Mechanicus**; эти встроенные данные требуется изменить на стенде.

## Известные ограничения

- Основное приложение всё ещё собрано в большом `src/app.py`.
- Существующие тесты используют старые пути `nmc_core` и `nmc_utils`.
- SSH-функции используют `paramiko`, но исходный `requirements.txt` его не содержит.
- В скриптах установки остались `pip --user`, настройка sudo и принудительное
  освобождение занятых портов; их необходимо пересмотреть перед обычным использованием.
- Сквозной VPN-сценарий и восстановление после перезагрузки ещё не проверены
  в рамках этого импорта.

Подробности и границы выполненных проверок: [состояние проекта](docs/STATUS.md).

## Ближайшая цель

Довести до повторяемого рабочего сценария:

1. Запустить Omnissiah с новой БД и зарегистрировать два Magos.
2. Создать соединение WireGuard и проверить handshake.
3. Добавить защищаемые подсети и применить политику доступа.
4. Проверить разрешённый и запрещённый трафик в обоих направлениях.
5. Сверить желаемую конфигурацию с фактически применённой.
6. Перезагрузить узлы и повторить проверки.

До завершения этого сценария приоритет — исправление существующей реализации.

## Что включено в импорт

Основой служит рабочее дерево `NMC_WG/` из предоставленного архива,
а не вложенные старые сборки. Исходники сервера и агента перенесены без
изменения логики. Добавлены описание, шаблон окружения и правила исключения файлов;
сборка архива ограничена файлами Git.

Не включены виртуальные окружения, IDE-настройки, кэши, базы данных, логи,
сертификаты, приватные ключи, `.env`, резервные копии и старые версии приложения.
База и секреты создаются локально при подготовке нового стенда.

Справочные документы исходного проекта доступны в [docs/reference](docs/reference/README.md).
Они сохранены как исторические материалы и могут расходиться с текущим кодом.
